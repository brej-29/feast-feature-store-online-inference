The idea

What is an online feature store?

A model is only as good as the data it sees at decision time. A feature store computes signals about each customer, merchant and device once, stores the freshest values in a fast database, and serves the same definitions to both training and live scoring — so the model never sees inconsistent inputs. Here's the request path:

1 Look up history

The customer, merchant, device and geo-cell keys are fetched from Postgres — counts, amounts, and matured fraud rates, all point-in-time correct.

2 Add the request

Signals available before the payment executes (amount, type, hour, pre-transaction balances) are combined with the stored features.

3 Score & decide

The model returns a fraud probability and a threshold decision, with the retrieval-vs-inference latency measured separately.

4 Stay fresh

A streaming path pushes each new event back into the store, so the next lookup already reflects what just happened.

The model

Honest numbers, leakage-safe features

Trained through Feast's point-in-time historical retrieval, so training and serving use identical feature definitions.

Trained on synthetic data — stated plainly

The dataset is PaySim, a simulator, so these metrics won't transfer to real payment traffic. The point of this project is the system — point-in-time correctness, online serving, streaming freshness — not the model score. Target leakage (a fraud-rate feature computed over the label) was found and removed; see the model card in the repo.

Under the hood

The stack

Feast feature store Postgres / Neon online store FastAPI + Pydantic scikit-learn (HistGBM) Kafka / Redpanda streaming Prometheus metrics Docker · Nginx · Render
  • Point-in-time correctness — every training row sees only features that existed before that transaction, with a 72-hour label-maturation delay on fraud signals.
  • One feature definition for training and serving via a shared Feast FeatureService, so serving can't silently drift from training.
  • Graceful degradation — if the online store is unavailable the API still scores from request-time features and flags the response.
  • Observability — per-stage latency, score distribution and streaming freshness are exported as Prometheus metrics.
